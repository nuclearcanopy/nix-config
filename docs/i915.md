# i915 display/GPU incidents (nidhoggr)

T480, i5-8350U, Kaby Lake-R GT2 (UHD Graphics 620, `8086:5917`), stock
`pkgs.linuxPackages`. Relevant module: `modules/boot/boot-t480.nix`.

Two different failures on this box share one visible signature, the sway
`Atomic commit failed: Device or resource busy` loop on eDP-1. They have
different causes and different fixes, so match on the *supporting* evidence
below rather than on the EBUSY line alone.

## 2026-11-01: GuC crash froze the desktop

**Symptom as experienced:** mouse cursor still moved, every window appeared
frozen, but the applications underneath were demonstrably still running and
responsive to input they could not display. Needed a restart.

**Chain, from `journalctl -b -1`:**

```
13:33:46  [wlr] connector eDP-1: Atomic commit failed: Device or resource busy
13:33:46  [sway] Page-flip failed on output eDP-1
13:34:16  i915: [drm] *ERROR* GT0: GUC: Crash dump notification
13:34:16  i915: [drm] *ERROR* GT0: GUC: Exception notification
13:34:16  i915: [drm] GPU HANG: ecode 9:0:00000000
13:34:16  i915: [drm] Resetting rcs0 for dead GuC
13:37:45  (GuC crash + GPU HANG, second time)
13:39:59  [wlr] [GLES2] GL_CONTEXT_LOST in context lost        <-- flood
```

**Why the symptom looks the way it does.** The GPU reset invalidates sway's
EGL/GLES2 context. wlroots has no recovery path for `GL_CONTEXT_LOST`; it keeps
submitting renders into a dead context indefinitely. sway itself never exits, and
the hardware cursor plane is moved by a separate ioctl that needs no GL, so the
pointer keeps tracking normally while no window surface is ever composited again.
Client processes are untouched, which is why they keep working invisibly.

The EBUSY burst preceding the hangcheck by ~30s is ordering, not a second cause:
the render engine was already wedged, commits started failing, and i915 hangcheck
only logged `GPU HANG` once its timeout expired.

**Root cause.** `i915.enable_guc=2`. On this gen9 part GuC *submission* is not
supported (`GT0: GUC: submission disabled` at every boot), so the flag's only
effect was loading `kbl_guc_70.1.1.bin` in order to authenticate
`kbl_huc_4.0.0.bin`. The kernel classifies the parameter as dangerous and taints
for it:

```
Setting dangerous option enable_guc - tainting kernel
```

That GuC firmware crashed under concurrent load (Steam and mpv were both running,
alongside a heavy parallel cargo build) and took the render engine with it.

**Fix.** Removed the parameter entirely, reverting to the driver default
`-1=auto`, which selects no GuC/HuC on Kaby Lake. **Cost:** no HuC-accelerated
low-power H.264/HEVC *encode*, which matters only for VA-API encoding such as OBS
or screen recording. Hardware video *decode* uses the fixed-function media engine
and is unaffected, so playback is unchanged.

**Explicitly ruled out:**

- *Memory pressure.* earlyoom logged 65-78% available RAM and >93% free swap
  across the whole window. The `steam[...] Fontconfig error: ... out of memory`
  lines are fontconfig's own message during Steam startup and are unrelated.
- *S3 resume degradation* (the 2026-07 failure below). Only **one**
  suspend/resume cycle had occurred in that boot, against the 4-6 that mode
  needs, and total EBUSY was **483** rather than the 20k-70k slow burn.

**Not changed, deliberately.** `i915.enable_psr=1` and `i915.enable_fbc=1`
(re-enabled 2026-08-22 for iGPU idle power) are the obvious next levers if a
repaint freeze recurs, and PSR in particular has a history of stale-screen bugs.
They were left alone so that a recurrence remains attributable to one variable.
If it does recur with GuC already off, set `i915.enable_psr=0` first.

**Residual risk.** The GuC was the trigger, not the fragility. *Any* future GPU
reset from any cause will freeze the desktop the same way, because the
unrecoverable part is wlroots' handling of `GL_CONTEXT_LOST`, not the GPU. There
is no fix for that at the config layer; it is an upstream limitation. Note the
session stays reachable over SSH when it happens, so restarting the compositor
remotely is a less drastic recovery than a power cycle.

## 2026-07-13 / 2026-07-15: S3 resume state degradation

Distinct failure, same EBUSY line. Characterised by 20k-70k EBUSY errors per boot
as a slow-burning baseline before a terminal hard lock, **no** kernel record at
all (no oops, no hung task, no i915 reset), and audio looping a buffer because
ALSA DMA kept replaying what userspace could no longer refill. Required a
force-shutdown.

Cause was S3 (deep) suspend/resume cycling, not display power wells: each resume
re-inits i915, and after ~4-6 of them a modeset returns EBUSY permanently.
`i915.enable_dc=0`, `enable_psr=0` and `enable_fbc=0` were all set at the time and
did not prevent it, because none of them addresses the D3cold transition the whole
GPU makes on S3.

Mitigated 2026-07-15 with `mem_sleep_default=s2idle`. That was **later reverted to
`mem_sleep_default=deep`** (currently active, `boot-t480.nix`) for the battery win
once no external display was in use, knowingly re-accepting the risk. If the
20k-EBUSY-plus-silent-kernel pattern returns, s2idle is the rollback.

Diagnostic to tell the two apart: `journalctl -b -1 -k | grep -c "GuC firmware"`
counts i915 re-inits, i.e. boots plus resumes. A climbing count with no GPU HANG
points at the S3 mode; a `GPU HANG` / `dead GuC` / `GL_CONTEXT_LOST` triad points
at the 2026-11-01 mode.
